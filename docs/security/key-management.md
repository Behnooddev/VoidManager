# Key management and encryption

Status: Proposed. No cryptographic code exists yet.

## Status

Implemented in `core:crypto` (Phase 3a) and tested outside Gradle against published test vectors: Argon2id (RFC 9106), HKDF-SHA256 (RFC 5869) and AES-256-GCM. The Android Keystore adapter, the unlock screens and calibration of the cost parameters on the device are not built yet (Phase 3b).

## Primitives

| Purpose | Choice | Library |
| --- | --- | --- |
| Password-based key derivation | Argon2id | Bouncy Castle (`Argon2BytesGenerator`) |
| Authenticated encryption of values | AES-256-GCM, random 96-bit nonce | Platform provider (`javax.crypto`) |
| Key derivation from a key | HKDF-SHA256 | Bouncy Castle (`HKDFBytesGenerator`) |
| Random values | `SecureRandom` | JDK / Android |
| Password text handling | Unicode NFKC, then UTF-8 | JDK |
| Large file encryption | Decided in Phase 7 | |
| Key agreement for sharing | Decided in Phase 8 (HPKE is the intent) | |

No custom constructions. Bouncy Castle is used through its lightweight API, so no security provider is registered. Tink, named in the first version of this design, is not used for now: nothing in Phase 3 needs more than the primitives above, and each dependency costs maintenance. It is reconsidered where streaming encryption (backups, media) or HPKE (sharing) is built.

Random nonces limit one key to roughly 2^32 messages. The field key protects individual values of one vault, which is far below that.

Argon2id parameters are stored in the key file next to the salt. Defaults: 64 MiB, 3 iterations, parallelism 1, 16-byte salt, 32-byte output. Accepted range when reading a key file: memory 19 MiB to 512 MiB, iterations 2 to 10, parallelism 1 to 8. The floor is the lowest Argon2id setting in current OWASP guidance; the ceiling stops a modified key file from requesting an amount of memory that crashes the application. Calibration on the device (raising the cost until a target unlock time is reached) is Phase 3b.

## Hierarchy

```
Master password  --Argon2id-->  KEK_pw
Device key (Keystore/OS store)  KEK_dev
Vault Key (VK, random 256-bit, generated at setup)

VK is stored wrapped twice:
  wrap(VK, KEK_pw)   always present
  wrap(VK, KEK_dev)  present when biometric/device unlock is enabled

HKDF(VK, "db")       -> database key (SQLCipher)
HKDF(VK, "field")    -> field encryption key (levels 2 and 3)
HKDF(VK, "media")    -> media encryption key
```

- Changing the master password re-wraps VK. Data is not re-encrypted.
- Rotating VK is a separate, explicit operation that re-encrypts everything. It is not part of the first release.
- Field ciphertext binds its context through associated data: `format version | table | row id | part key`. A ciphertext copied to another row fails authentication.
- Nonces are generated by the library per encryption. No counters kept by application code.

## Key file

The wrapped vault key lives in a small binary file next to the database (`vault.keys`), because it is needed before the database can be opened. Layout: magic `VMKF`, format version, Argon2id cost, salt, password-wrapped key, optional device-wrapped key. The header up to and including the salt is bound into the password wrap as associated data, so changing the cost parameters or the salt makes unwrapping fail instead of silently weakening the derivation. The file is written to a temporary file, synced and moved into place, so an interrupted write leaves the old file.

## Password handling

- The password is normalized to Unicode NFKC before encoding as UTF-8, so the same typed password derives the same key whichever form the keyboard produced. The normalized text is a temporary string that cannot be overwritten.
- Changing the password asks for the current password again even when the vault is unlocked, and re-wraps the vault key under a new salt. Stored data is not re-encrypted.
- Minimum length 12 by default, never below 8; very common passwords, a single repeated character and simple sequences are refused. The strength value is a heuristic estimate, not a guarantee.
- A wrong password and a modified key file cannot be told apart and produce the same result.

## Unlock paths

1. Master password: derive KEK_pw, unwrap VK.
2. Biometric or device credential: an Android Keystore key (StrongBox when available) that requires user authentication unwraps VK. The key is configured to be invalidated when biometric enrollment changes; the user then unlocks with the master password and re-enables biometrics.
3. Desktop: master password. OS credential stores may hold KEK_dev if the user opts in.

## Lock behavior

- The app locks on request, on background after the configured timeout, and on idle timeout.
- Locking drops the VK and derived keys from memory (byte arrays are zeroed), closes the database, cancels in-flight reveal states, and clears sensitive UI state. Navigation returns to the lock screen.
- Limitation: the JVM does not guarantee that no copies of key material remain in memory. Zeroing reduces exposure; it does not make memory forensics on an unlocked device impossible.

## Screens and lock behavior in the app (0.4.0)

- `VaultFlow` (`app:shared`) is the lock state machine: no vault, locked, unlocked. It has no UI and no threads and is covered by unit tests; `VaultController` publishes its state to Compose and runs key derivation on a worker thread.
- On Android the controller is owned by the `Application`, so a rotation does not lock the vault. The app locks as soon as the activity stops for any reason other than a configuration change, and after 60 seconds without a touch or key press while in the foreground.
- Wrong passwords: after the fourth failure each further failure imposes a wait (5 seconds, doubling, capped at 5 minutes). The counter is in memory and restarts with the process. It is a usability measure, not a security boundary: an attacker with a copy of the files attacks the key file offline, where only the Argon2id cost and the password strength matter.
- Passwords are typed into a text field that holds a `String`, which cannot be overwritten. The `CharArray` copy passed to the vault is overwritten as soon as the call returns. Password text is kept in plain `remember` state, never `rememberSaveable`, so it is not written to saved instance state.
- `FLAG_SECURE` is always on for the Android window. A setting to allow screenshots is not planned.
- Screens that edit data must call `VaultController.onInteraction()` on text changes, because typing on the soft keyboard does not produce touch events and would otherwise let the idle timer lock the vault in the middle of an edit.

## Recovery limits

- There is no server and no recovery service. A forgotten master password cannot be reset by anyone.
- Backups are the recovery path for data loss, and they have their own password (see `backup-format.md`).
- An optional printed or saved recovery key that wraps VK is a possible feature. It is not in the specification and is listed in `open-decisions.md`.

## What the master password protects

The master password strength determines resistance to offline attacks against a copied database or backup. The setup screen enforces a minimum length and shows an estimate. The exact policy is set in Phase 5.

## Encryption boundaries

- Encrypted at rest: database (SQLCipher), level 2 and 3 values (per value), media and attachments (per file), backups, share packages.
- Not encrypted: non-personal settings, the app binary, and (necessarily) data while displayed or in memory after unlock.
- Exports (CSV, XLSX, PDF) are plaintext files by nature. They are outside the encryption boundary once written, and the export UI says so.
